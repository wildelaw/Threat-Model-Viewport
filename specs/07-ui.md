# 07 — User Interface

The Carbon shell, the nine tabs, the per-tab side navigation, and the screen inventory.

**Read this first:** Carbon v11 supplies CSS only. There is no JavaScript bundle — no UMD build, and
the Web Components are code-split ES modules that cannot be inlined. Every behaviour in this document
is hand-written vanilla JS that toggles Carbon's own state classes. §5 is the inventory of that work,
and it is the largest single body of implementation in the project.

Related: ADR-0002 (Carbon via CDN), ADR-0007 (navigation model), REQ-UI-001..012.

| Region | Carbon classes | Notes |
|---|---|---|
| Header | `cds--header`, `cds--header__name`, `cds--header__nav`, `cds--header__action`, `cds--header__menu-trigger` | Fixed 48px |
| Tabs | `cds--tabs`, `cds--tab--list`, `cds--tabs__nav-item`, `cds--tabs__nav-link` | `contained` or line variant |
| Side nav | `cds--side-nav`, `cds--side-nav__items`, `cds--side-nav__item`, `cds--side-nav__link` | 16rem; 3rem when collapsed |
| Content | `cds--content`, `cds--grid` | `#tmv-content` |

### Deviation from Carbon's tabs markup, and why it matters

Carbon's tab component expects **one panel per tab**, all present, with the inactive ones hidden.

This application does not do that. Rendering nine panels and hiding eight wastes the work of building
them, and the content is derived from a model that changes — so hidden panels would need invalidating.
Instead, the tab strip is a selector and **one** content region is rendered into.

The accessibility consequence has to be handled deliberately, not inherited:

- The tab strip keeps `role="tablist"` and each tab keeps `role="tab"` with `aria-controls="tmv-content"`.
- `#tmv-content` keeps `role="tabpanel"`, and its `aria-labelledby` is **updated on every tab switch**
  to the active tab's id.
- Roving `tabindex` applies: only the active tab is in the tab order; arrow keys move between tabs,
  `Home`/`End` jump to the ends.

That is a legal composition — multiple tabs controlling one panel — but it is **not** the markup
Carbon's documentation shows, so it will not match the examples and must not be assumed correct on
that basis. It is called out in `09-testing.md` as a specific accessibility review item rather than
left to the generic axe pass.

> **Verify against the compiled stylesheet:** the exact state classes for the tab strip, side nav
> (`.is-visible` vs `--expanded`), and modal (`is-visible`) must be read from the pinned Carbon
> stylesheet rather than from documentation, which describes the React implementation's conventions.
> Treat every class name in §5 as "confirm before relying on".

## 2. Top tabs

Nine tabs (REQ-UI-002). Order is deliberate: model content first, mechanics last.

| # | Tab | Purpose |
|---|---|---|
| 1 | **Overview** | What this model is: scope, metadata, contributors, and readiness to export |
| 2 | **Architecture** | Zones, boundaries, components, actors, data stores — and the diagram |
| 3 | **Data** | Data sets and OTM assets, with sensitivity and CIA ratings |
| 4 | **Flows** | Data flows, their properties, and where they cross trust boundaries |
| 5 | **Threats** | Threats, personas, assumptions, and every threat-to-target link |
| 6 | **Controls** | Countermeasures, their status, and what they cover |
| 7 | **Risk** | The risk matrix, the risk register, and the rating inputs |
| 8 | **History** | Commits, comparison, conflicts, stashes, and integrity |
| 9 | **Settings** | Identity, storage, import/export, diagram behaviour, appearance, danger zone |

### Where the diagram lives

The diagram is a **sub-section of Architecture**, not its own tab, even though it is arguably the
most-viewed screen. It is a view *of* the architecture, and giving it a tab would imply it is a
separate subject. It is also reachable in one click from Overview via a "View diagram" action, which
covers the common case without spending a tab on it.

## 3. Side navigation, per tab

The side nav holds the sub-sections of the **active** tab (REQ-UI-003), one level deep — Carbon's
side nav supports no third tier, and nesting further would require abandoning the component.

| Tab | Side-nav entries |
|---|---|
| **Overview** | Summary · Scope · Contributors · Export Readiness · Provenance |
| **Architecture** | Trust Zones · Trust Boundaries · Components · Actors · Data Stores · **Diagram** |
| **Data** | Data Sets · Assets · Sensitivity · Placement |
| **Flows** | All Flows · Unencrypted · Cross-Zone · Missing Endpoints |
| **Threats** | All Threats · By Target · By Persona · Personas · Assumptions · Unresolved References |
| **Controls** | All Controls · By Threat · Mitigation Plans · Coverage Gaps · Unapplied |
| **Risk** | Risk Matrix · Risk Register · Threat Risk Inputs · CIA Ratings · Trust Ratings |
| **History** | Log · Compare & Merge · Conflicts · Stashes · Integrity |
| **Settings** | Identity · Storage · Import · Export · Diagram · Appearance · About · Danger Zone |

Two entries are cross-cutting and appear in more than one tab, deliberately:

- **Unresolved References** (Threats) and **Missing Endpoints** (Flows) surface the referential
  problems from REQ-VIEW-007 in the context where the user would look for them.
- **Export Readiness** (Overview) is the same list as §`06-interchange.md` §8, which also appears
  inside the export dialog. It is the one screen that shows *both* formats' gaps at once.

Entries that are filters rather than entity types — *Unencrypted*, *Cross-Zone*, *Coverage Gaps* —
are marked with a count so they read as findings, not sections. An empty filter showing `0` is
informative; an empty filter showing nothing looks broken.

### Contents are regenerated, state is preserved

The nav's entries change with the tab; its scroll position, and whether it is collapsed, do not
(REQ-UI-003 AC3). Collapsed state is stored in preferences and applies across tabs — a user who
collapsed the rail to see more table width does not want it re-expanded by switching tabs.

## 4. Header

| Control | Behaviour |
|---|---|
| App name | Static. No link — there is nowhere to navigate to |
| **Model switcher** | Dropdown listing registry entries plus the embedded model (REQ-UI-004) |
| Dirty indicator | Visible when the working copy differs from the head (REQ-EDIT-005) |
| **Commit** | Primary action. Disabled when clean, with a tooltip saying why |
| **Import / Export** | Overflow menu — both are infrequent and neither deserves header space |
| **Theme** | Overflow menu, four Carbon themes (REQ-UI-005) |
| Storage warning | Appears in the header when storage is degraded, so it is visible from every tab |

### The model switcher

Entries, in order:

1. **The embedded model** — always first, marked `From file`. This makes the file's own model
   reachable even when storage is empty or partitioned, which is the mechanism that keeps REQ-STORE-004
   working on Firefox.
2. Registry entries, most recently opened first.

Each entry shows name, commit count, and last-opened time. A **delete** affordance appears on
registry entries only, and is **absent** — not present-and-disabled — for the embedded model, with the
menu explaining that it comes from the file (REQ-UI-004 AC2).

Switching with a dirty working copy prompts to commit, stash, or discard (REQ-STORE-004 AC1). Never
silently.

### Deliberately not used

| Component | Why |
|---|---|
| **Date picker** | Carbon's calendar is flatpickr; the CSS theme ships but the JS does not. A Carbon-styled native `<input type="date">` gives a working picker in every target browser with no dependency. Dates in this model are day-granularity, so the loss is nil |
| **Carbon Charts** | Charts are a separate package with no vanilla single-file build; the network/diagram building blocks are React-and-Angular only and Carbon explicitly does not provide layouts. Not worth a third dependency for a 5×5 matrix that is a grid of labelled cells |
| **Web Components** | Code-split ES modules — they cannot be inlined, and they would add a runtime CDN dependency per component |
| **Carbon React** | No UMD build, ~18 unbundled dependencies, React as a peer. Incompatible with a single file |

### The 5×5 risk matrix

Built from Carbon tokens rather than a charting library: a `cds--css-grid` of 25 cells, each a
`cds--tag`-styled block, with the risk level driving the tag colour. Carbon's tag colour set maps
cleanly onto the six levels, and this keeps the whole feature at ~40 lines with no dependency.

Colour is never the sole carrier of meaning (REQ-UI-007 AC4): each cell carries its score as text and
its level as an accessible label, so the matrix survives greyscale and colour-blindness.

### The diagram

Rendered by us into an `<svg>`, not by a Carbon component — Carbon has no graph component.

| Source | Rendering |
|---|---|
| OTM coordinates (`representations` + `representationElements`) | Native SVG: zones as labelled rectangles, components as boxes inside their zone, flows as lines between element centres. Pan and zoom are ours |
| TML `svg` diagrams | Sanitized, then inlined (REQ-SEC-004) |
| TML `mermaid` diagrams | Rendered by Mermaid, **lazily loaded from the pinned CDN on first display** (REQ-VIEW-005) |
| TML `graphviz` / `plantuml` | Source text in a `cds--snippet`, with a copy action. Not rendered |
| None | Empty state explaining that this model has no diagram data, naming the source format |

Mermaid being lazy is a requirement, not an optimisation: it is a large dependency and most models
never need it. It is also the third and last permitted network origin (REQ-SHELL-007), added to the
CSP only when the feature is used.

### Compare & merge

The most complex screen and the one most likely to be got wrong. Layout:

```
┌──────────────────────────────────────────────────────────────┐
│ Base: C3 (sha256:7a2f…)   │  A: file (C5)  │  B: local (C7)   │
├──────────────────────────────────────────────────────────────┤
│ 2 added · 5 changed · 0 removed          [ filter: conflicts ]│
├──────────────────────────────────────────────────────────────┤
│ ▸ Threat "SQL Injection"        both changed, different fields│
│     description   base→…   A→…   B→…            [ A ] [ B ]  │
│     likelihood    base→50  A→75  B→50           [ A ] [ B ]  │
│ ▸ Component "API Gateway"       only A changed     [ A ] [base]│
│ ▸ Control "WAF rules"           CONFLICT in status  [ A ] [ B ]│
└──────────────────────────────────────────────────────────────┘
```

- Default view filters to **conflicts only**, because a routine reconcile is mostly non-conflicting
  and the user's attention should go where a decision is actually needed. A toggle shows everything.
- Non-overlapping changes are **pre-selected as a suggestion** and clearly labelled as such. Nothing
  is written until confirm (REQ-VCS-009 AC2).
- Conflicts have **no pre-selection** — the user must pick.
- Deletions are presented as an explicit choice, never as a default.

## 7. Responsive behaviour

Carbon's 2× grid: `sm` 320px/4 cols · `md` 672px/8 · `lg` 1056px/16 · `xlg` 1312px/16 · `max` 1584px/16.

| Breakpoint | Layout |
|---|---|
| `max`, `xlg`, `lg` | Full: side nav expanded at 16rem, full tab row, tables at default size |
| `md` | Side nav collapses to the 3rem rail by default; tables switch to a compact size |
| `sm` | Side nav becomes an overlay opened from the header trigger; tab row scrolls horizontally; tables become cards |

No horizontal page overflow at 320px (REQ-UI-006 AC2). Data tables are a real constraint here — entity
tables have many columns — so at `sm` they switch to a stacked card presentation rather than a
horizontally-scrolling table, because a threat model's rows are read as records, not compared
column-wise.

## 8. Accessibility

Target: WCAG 2.1 AA (REQ-UI-007). Carbon's markup is accessible; hand-written behaviour is where that
is lost, so the following are explicit obligations rather than assumptions:

| Obligation | Where it bites |
|---|---|
| Focus is trapped in modals and overflow menus, and **restored** to the invoking element on close | Every modal, the switcher, overflow menus |
| Roving tabindex on tabs and the data table | Tab strip, tables |
| `aria-expanded`, `aria-controls`, `aria-activedescendant` on all disclosure and listbox patterns | Dropdowns, trees, accordions, side nav |
| Live regions announce commit, reconcile, import, export, and error outcomes | REQ-UI-009 |
| Destructive modals place initial focus on the **cancel** action | Delete, discard |
| Risk level is conveyed by text, not colour alone | Risk matrix, tags, status indicators |
| Every icon-only control has an accessible name | Header actions, close buttons |
| Table sort state is announced, not just shown by a caret | Data table |

Two items need review beyond automated tooling, because axe cannot judge them:

1. The **single-panel tabs** composition (§1) — correct `aria-labelledby` on every switch.
2. The **compare & merge** screen — a three-column diff is hard to navigate by keyboard and hard to
   follow with a screen reader. It needs a deliberately designed linear order, not a table.

## 9. Cross-cutting states

| State | Presentation |
|---|---|
| **Empty model** | Overview explains the model has no content yet and offers import; other tabs show informative empty states, never errors (REQ-VIEW-001 AC2) |
| **Empty filter result** | "No threats matching *unencrypted*" with a clear-filter action — distinct from empty-model, because the cause is different |
| **Read-only** | A persistent banner naming the reason; all edit affordances removed, not disabled (REQ-VIEW-008) |
| **Dirty** | Header indicator + `beforeunload` warning (REQ-EDIT-005) |
| **Storage degraded** | Header warning, visible from every tab (REQ-STORE-007) |
| **Unresolved references** | Warning indicator on the entity, in list and detail, naming the missing target (REQ-VIEW-007) |
| **Integrity failure** | Full-screen read-only, naming the commit, export still available |
| **Large model** | Virtualised or paginated lists; a "still working" indicator past 300 ms (REQ-VIEW-009) |

Two of these deserve a note on tone. The **storage degraded** and **origin partitioned** notices will
be the most common confusing moment in the product (REQ-SYNC-008), and they are the difference between
"this tool is broken" and "this tool explained something I did not know about my browser". They are
written in plain language, name the browser behaviour, and always offer the file-based path — they
never say "storage error".

## 10. What the UI deliberately does not do

- **No URL routing.** `pushState` is unreliable on `file://`. Tab and sub-section state live in memory
  and in preferences, so a reload returns to where you were but a URL is not shareable. This is a real
  limitation of the file-based model and is stated in About.
- **No drag-to-rearrange on the diagram.** v1 renders; it does not author. Geometry from an imported
  OTM file is preserved and re-exported unchanged (see `00-overview.md`, non-goals).
- **No dark-mode auto-switching beyond first run.** The theme is chosen once from the OS preference
  and then remembered, rather than following the OS continuously — a user who picked Gray 100 on a
  light-mode machine meant it.
- **No keyboard shortcuts beyond standard navigation.** Worth revisiting; see
  `10-open-questions.md`.
